## 第三题：计算机网络-TCP协议

### 涉及知识点

#### 1. TCP协议特点

- **面向连接**：通信前需建立连接
- **可靠传输**：确保数据按序无差错到达
- **全双工通信**：双向数据传输
- **面向字节流**：无消息边界
- **流量控制**：滑动窗口机制
- **拥塞控制**：慢开始、拥塞避免、快重传、快恢复

#### 2. TCP报文段格式

- **源端口**（16位）、**目的端口**（16位）
- **序号seq**（32位）：本报文段第一个字节的序号
- **确认号ack**（32位）：期望收到的下一个字节序号
- **数据偏移**（4位）：首部长度
- **标志位**（6位）：

  - URG：紧急指针有效
  - **ACK**：确认号有效
  - PSH：尽快交付应用层
  - RST：重置连接
  - **SYN**：同步序号，建立连接
  - **FIN**：释放连接
- **窗口**（16位）：接收窗口大小
- **校验和**（16位）
- **紧急指针**（16位）

#### 3. TCP三次握手（建立连接）

```text
客户端                           服务器
  |                                 |
  |  SYN=1, seq=x                  |
  |------------------------------->|  (1) SYN_SENT
  |                                 |  (2) SYN_RCVD
  |  SYN=1, ACK=1, seq=y, ack=x+1 |
  |<-------------------------------|
  |                                 |
  |  ACK=1, seq=x+1, ack=y+1      |
  |------------------------------->|  (3) ESTABLISHED
  |                                 |  ESTABLISHED
```

**过程**：

1. **第一次握手**：客户端发送SYN=1，seq=x（随机初始序号）

   - 客户端进入SYN\_SENT状态
2. **第二次握手**：服务器发送SYN=1，ACK=1，seq=y，ack=x+1

   - 服务器进入SYN\_RCVD状态
3. **第三次握手**：客户端发送ACK=1，seq=x+1，ack=y+1

   - 双方进入ESTABLISHED状态

**为什么需要三次？**

- 防止失效的连接请求到达服务器（如第一次握手延迟到达）
- 确认双方的发送和接收能力都正常
- 协商初始序列号

#### 4. TCP四次挥手（释放连接）

```text
客户端                           服务器
  |                                 |
  |  FIN=1, seq=u                  |
  |------------------------------->|  (1) FIN_WAIT_1
  |                                 |  (2) CLOSE_WAIT
  |  ACK=1, seq=v, ack=u+1        |
  |<-------------------------------|  FIN_WAIT_2
  |                                 |
  |  FIN=1, ACK=1, seq=w, ack=u+1 |
  |<-------------------------------|  (3) LAST_ACK
  |                                 |
  |  ACK=1, seq=u+1, ack=w+1      |
  |------------------------------->|  (4) TIME_WAIT
  |                                 |  CLOSED
  |  (等待2MSL)                     |
  |                                 |
CLOSED                              |
```

**过程**：

1. 客户端发送FIN=1，seq=u，进入FIN\_WAIT\_1
2. 服务器发送ACK=1，ack=u+1，进入CLOSE\_WAIT；客户端进入FIN\_WAIT\_2
3. 服务器发送FIN=1，ACK=1，seq=w，ack=u+1，进入LAST\_ACK
4. 客户端发送ACK=1，ack=w+1，进入TIME\_WAIT，等待2MSL后CLOSED

**为什么需要四次？**

- TCP是全双工，需要双向关闭
- 第2、3次可能合并（服务器立即关闭时）

**TIME\_WAIT状态**：

- 时长：2MSL（Maximum Segment Lifetime，通常2分钟）
- 目的：

  - 确保最后的ACK能到达服务器
  - 让旧连接的所有报文段消失

#### 5. TCP可靠传输机制

**1) 序号和确认**

- 每个字节都有序号
- ACK确认收到的字节

**2) 超时重传**

- 发送方设置重传定时器
- 超时未收到ACK则重传
- 动态计算RTO（重传超时时间）

**3) 滑动窗口**

- 发送窗口：已发送未确认 + 可发送
- 接收窗口：可接收的序号范围
- 实现流量控制和高效传输

**4) 快重传**

- 收到3个重复ACK立即重传
- 不等超时

**5) 选择确认SACK**

- 告知发送方哪些数据已收到
- 减少不必要的重传

#### 6. TCP流量控制

- 接收方通过窗口字段通告可用缓冲区大小
- 发送方根据接收窗口调整发送速率
- 防止接收方缓冲区溢出

#### 7. TCP拥塞控制

**拥塞窗口cwnd**：发送方维护，限制发送速率

**四个算法**：

**1) 慢开始**

- 初始cwnd = 1 MSS
- 每收到一个ACK，cwnd加1
- 指数增长：1 → 2 → 4 → 8 → ...
- 达到慢开始门限ssthresh时，转为拥塞避免

**2) 拥塞避免**

- 每经过一个RTT，cwnd加1
- 线性增长：n → n+1 → n+2 → ...

**3) 快重传**

- 收到3个重复ACK，立即重传
- 不等超时

**4) 快恢复**

- 快重传后：

  - ssthresh = cwnd / 2
  - cwnd = ssthresh
  - 直接进入拥塞避免（不回到慢开始）

**超时处理**：

- ssthresh = cwnd / 2
- cwnd = 1
- 重新慢开始

### 根据回忆补全的题目

**题目**：关于TCP协议，回答以下问题：

1. 简述TCP三次握手的过程，并解释为什么不能是两次握手？
2. 在TCP连接中，客户端发送了一个长度为1000字节的数据段（seq=2000），服务器正确接收后应该返回什么确认号？
3. 假设TCP使用慢开始和拥塞避免算法，初始ssthresh=16（单位MSS），描述cwnd的变化过程直到第一次出现超时，并画出cwnd随时间变化的示意图。
4. TIME\_WAIT状态的作用是什么？为什么要等待2MSL的时间？

### 详细解析

#### 解答1：三次握手过程

**过程**：

1. 客户端发送：SYN=1, seq=x（随机初始序号）
2. 服务器回复：SYN=1, ACK=1, seq=y, ack=x+1
3. 客户端确认：ACK=1, seq=x+1, ack=y+1

**为什么不能是两次？**

**问题1：无法确认客户端的接收能力**

- 两次握手：客户端发SYN → 服务器回SYN+ACK → 连接建立
- 服务器无法确认客户端是否收到了自己的SYN+ACK
- 如果SYN+ACK丢失，服务器认为连接建立，客户端却不知道

**问题2：失效的连接请求**

- 场景：客户端发送SYN1，网络延迟很久才到达
- 客户端超时后重发SYN2，建立连接并完成通信，关闭连接
- 此时SYN1才到达服务器
- 两次握手：服务器回复ACK后认为连接建立，等待数据，但客户端不会发送
- 三次握手：服务器回复SYN+ACK后，等不到客户端的第三次握手，不会建立连接

**问题3：无法协商双方的初始序列号**

- TCP需要双方都确认对方的初始序列号
- 两次握手无法保证客户端知道服务器已收到并确认了自己的序列号

#### 解答2：确认号计算

- 客户端发送：seq=2000, length=1000
- 数据占用序号：2000~2999（共1000个字节）
- 服务器期望收到的下一个字节序号：3000
- **服务器返回确认号：ack=3000**

#### 解答3：cwnd变化过程

**初始条件**：

- cwnd = 1 MSS
- ssthresh = 16 MSS

**变化过程**：

**慢开始阶段**（cwnd \< ssthresh）：

- RTT 1: cwnd = 1 → 2
- RTT 2: cwnd = 2 → 4
- RTT 3: cwnd = 4 → 8
- RTT 4: cwnd = 8 → 16（达到ssthresh）

**拥塞避免阶段**（cwnd ≥ ssthresh）：

- RTT 5: cwnd = 16 → 17
- RTT 6: cwnd = 17 → 18
- RTT 7: cwnd = 18 → 19
- ...
- 继续线性增长，直到出现超时

**假设RTT 12时出现超时**：

- 此时cwnd = 23
- 超时后：

  - ssthresh = cwnd / 2 = 23 / 2 = 11（向下取整）
  - cwnd = 1
  - 重新慢开始

**示意图**：

```text
cwnd
 24 |                    /○ (超时)
 20 |                  /
 16 |           ○----/
 12 |         /
  8 |     ○
  4 |   ○
  2 | ○
  1 |○                        ○ (重新开始)
    +--------------------------> RTT
      1  2  3  4  5  6 ...12  13
      ←慢开始→←拥塞避免→
```

#### 解答4：TIME\_WAIT状态

**作用1：确保最后的ACK能到达**

- 四次挥手中，客户端发送最后的ACK后进入TIME\_WAIT
- 如果这个ACK丢失，服务器会重传FIN
- TIME\_WAIT期间可以接收并重发ACK
- 如果立即关闭，服务器重传的FIN会收到RST，导致服务器异常

**作用2：让旧连接的报文段消失**

- 确保本连接的所有报文段都从网络中消失
- 防止旧连接的延迟报文段出现在新连接中（如果新连接使用相同的端口）

**为什么是2MSL？**

- MSL（Maximum Segment Lifetime）：报文段最大生存时间
- 最坏情况：

  - 客户端发送ACK用时1 MSL
  - 服务器重传FIN用时1 MSL
- 共2 MSL可确保双向报文都消失
- 典型值：MSL = 2分钟，2MSL = 4分钟（Linux中常为60秒）

#### 练习3

解释TCP为什么是面向字节流而不是面向消息的？这会带来什么问题？如何解决？

点击查看答案

**面向字节流的含义**：- TCP把应用层数据看作无结构的字节序列 - 不保留应用层的消息边界 - 发送方可能将多个write()的数据合并成一个TCP报文段 - 接收方可能需要多个read()才能读完一个应用层消息 **对比面向消息**：- UDP是面向消息的 - 每个sendto()对应一个UDP数据报 - 接收方每个recvfrom()接收一个完整消息 **带来的问题**：- **粘包**：多个应用层消息被合并 - **拆包**：一个应用层消息被拆分 - 应用层无法直接区分消息边界 **解决方案**： 1. **固定长度**：每个消息固定N字节 2. **特殊分隔符**：用\\n、\\r\\n等分隔消息 3. **长度前缀**：消息头部包含长度字段 `[4字节长度][消息内容]` 4. **应用层协议**：如HTTP的Content-Length **示例代码（长度前缀）**：# 发送 def send\_message(sock, msg): msg\_bytes = msg.encode() length = len(msg\_bytes) sock.sendall(length.to\_bytes(4, 'big') + msg\_bytes) # 接收 def recv\_message(sock): length\_bytes = sock.recv(4) length = int.from\_bytes(length\_bytes, 'big') msg\_bytes = sock.recv(length) return msg\_bytes.decode()
